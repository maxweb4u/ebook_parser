# Testing Policy

What must be covered automatically, what is checked by hand, and why the line
sits where it does. Per-feature criteria live in that feature's brief; this
document states the standing rule.

## Current Coverage

the code being extracted — `book_parsing_test.dart` (149 lines), 
`book_archive_test.dart` (131), `book_document_codec_test.dart` (64) — written
against `flutter_test`, building their inputs in code. They port to
`package:test` with the assertions intact.

## What Must Be Tested

This is a library other people install, so the public surface is the test
surface. Automated coverage is required for:

- **Every exported name**, in the shape the README shows it. A published API
  without a test is a promise nobody checked.
- **Both formats, symmetrically.** Any behaviour claimed for one format is
  asserted for the other. Convergence is the package's premise, and the place it
  breaks is one parser quietly doing something the other does not — which is how
  the cover divergence survived until it was read for.
- **Failure paths.** Malformed input returns `ParseErr` and never throws. Corrupt
  inputs are generated by mutating valid ones, so the coverage is systematic
  rather than a handful of broken files someone thought of.
- **The properties that are the product.** Laziness of segmentation, the metadata
  path not inflating chapters, and a document surviving an isolate boundary are
  not incidental behaviours; they are what the package is chosen for, and each
  would break silently under refactoring. Each has a test whose failure says so.
- **Anything a version number promises.** The encoded form is pinned to
  `kBookDocumentSchemaVersion` by a golden test, so changing the shape without
  bumping the version fails.
- **Real books, not only synthetic ones.** Golden files from real producers per
  format variant, because a constructed sample confirms only what we already
  believed about the format.

CI runs `dart analyze`, `dart test`, and `dart pub publish --dry-run` on every
push. All three are required to pass.

- **Structural edge cases, adversarially.** A green corpus run proves producer
  coverage, not structural correctness: seven adversarial review passes on
  2026-09-01 fixed ~20 confirmed bugs after acceptance while the 636-book corpus
  stayed green through every one of them (yield 4 → 7 → 7 → 3 → 2 → 1 → 0,
  stopping at the first clean pass). The probes that pay are contract-driven:
  self-closing elements, nested same-name elements, namespace prefixes,
  duplicate ids, minified markup — and the FB2 `parse`/`parseMetadata` parity
  contract is the single highest-yield place to point them. Every find is
  pinned in `test/regression_fixes_test.dart`.

## What Is Verified Manually

- **Corpus behaviour.** Running the reader across a collection of real books and
  looking at what comes out. No assertion captures "the chapters are in a sane
  order and the text reads like the book"; a person notices in seconds what a
  test cannot express.
- **README accuracy.** That the format-support table and the per-writing-system
  segmentation table match what the code does. Reviewed against the decisions
  they describe, not against the code's own opinion of itself.
- **pub.dev presentation.** The rendered page, the example, and the score
  breakdown, once, before the first publication.

## Verification For New Work

| Kind of change | What closes it |
| --- | --- |
| New exported name | Test per behaviour, doc comment, README mention if a user would look for it |
| Parser change | Both formats asserted, plus a golden file if the change was prompted by a real book |
| Model change | Codec round-trip, schema version bumped, isolate transport still passing |
| Segmenter change | A case per affected writing system; the laziness assertion still green |
| Dependency change | `dart pub get` and `dart test` in a scratch pure-Dart project with no Flutter SDK present |

A change that alters the encoded form or the exported surface is not closed until
`CHANGELOG.md` says so.

## Simplify Review

After functional verification passes and before acceptance or closure, perform a separate simplify review. Confirm that the implementation is minimally complex; prefer a few clear repeated lines over premature abstraction. Keep additional complexity only when a constraint, invariant, failure mode, accepted local decision, or ADR justifies it.

For this package the recurring temptation is options. An optional parameter on a
published API is permanent, doubles the test matrix, and is usually added on
behalf of a consumer who has not asked. Adding one later is not a breaking
change; removing one is. Default to documenting the behaviour and waiting.

## Verification Context Separation

Functional verification, simplify review, and acceptance are three logically separate passes. They may happen in one session, but state the conclusion of each pass before starting the next one.
